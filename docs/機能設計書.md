## 2. 実行制御設計

### 2.1 起動契機

| 契機 | 説明 |
|---|---|
| schedule (cron) | 15分間隔。UTC `*/15 0-14,21-23 * * *` ＝ **JST 6:00〜23:45**（JST 0:00〜6:00 は起動しない＝要件5.2の深夜停止） |
| workflow_dispatch | GitHub Actions 画面からの手動実行（動作確認用） |
| ローカルCLI | `python src/monitor.py [オプション]`（開発・検証用、3章CLI参照） |

### 2.2 二重ガード

- **多重実行防止**：workflow の `concurrency.group: monitor`（前の実行中は次を待機、キャンセルしない）
- **稼働時間ガード**：スクリプト側でも `active_hours`（JST 06:00–24:00）外なら何もせず正常終了（cron設定ミス時の安全弁）

### 2.3 Tier（層別監視）の判定 — `select_facilities()`

| `--tier` | 対象 |
|---|---|
| `auto`（既定） | Tier 1 は毎回。**Tier 2 は前回のTier 2実行から55分以上経過していた場合のみ**併せて実行 |
| `1` / `2` / `all` | 指定層のみ／全件（検証用） |

- Tier 2 の実行時刻は `state.meta.last_tier2_run`（ISO形式）に記録し、**実行が成功扱いのときだけ更新**する（失敗時は次回に再実行される）
- 「毎時0分の実行か」ではなく経過時間で判定するため、GitHub Actions の cron 遅延・スキップに対して頑健

### 3.2 関数一覧

| 関数 | 役割 |
|---|---|
| `log(msg)` | JST時刻つき標準出力（Actionsログ＝要件F-7） |
| `parse_hhmm` / `parse_range` | `"HH:MM"`／`"HH:MM-HH:MM"` を0時起点の分に変換（`24:00`=1440対応） |
| `in_active_hours(cfg, now)` | 稼働時間内か判定 |
| `slot_in_windows(windows, date, start, end)` | 枠が曜日別通知時間帯と**一部でも重なるか**判定。重なり条件は `枠開始 < 窓終了 AND 枠終了 > 窓開始`（境界接触は重ならない扱い）。終了≦開始の枠は日跨ぎとみなし終了に+24h |
| `build_payload(purpose_ids, purposes_cfg, start, end)` | GetDay API のリクエストJSONを組み立て（利用目的は複数同時指定可） |
| `request_headers()` | UA・Accept・X-Requested-With・Referer |
| `fetch_day(lgc, fc, payload)` | GetDay API 呼び出し。**試行ごとに新規セッション**・最大2試行（リトライ前に20秒待機）。HTTP≠200、非JSON応答（WAF/混雑検知）、`rooms`/`timeFrames` 欠落（仕様変更検知）は失敗扱い |
| `extract_slots(fc, data)` | レスポンス → 枠辞書に展開。時間枠IDは同梱の `timeFrames` で実時刻に解決 |
| `diff_new_availability(prev, curr, notify_statuses)` | **「非空きステータス → 空きステータス」への遷移**のみ抽出。前回に存在しないキーは対象外（=F-2の初回・新規日付の通知抑止） |
| `annotate_consecutive(curr_slots, hits, notify_statuses, min_minutes)` | **連続時間判定（F-8）**。同一コート・同一日の空き枠を「前枠の終了＝次枠の開始」で連結した塊（run）を構築し、通知候補のうち合計 `min_minutes` 以上の塊に属するものだけを残す。塊の範囲を `info["block"]` に付与。`min_minutes<=0` で無効化（素通し） |
| `format_item_line(info)` | 通知1行を整形：`6/14（日） 13:00–14:00 サッカー場 東サッカー場（予約申込可）`。塊が枠単独より広い場合は `（予約申込可／連続枠 14:00–16:00）` の形式で付記 |
| `build_notification_embeds(groups, lgc)` | 施設ごとにfield化し Discord embed を構築（4.2参照） |
| `send_discord(webhook, embeds)` | 10 embeds/メッセージ20で分割送信。HTTP 429 は Retry-After（上限10秒）で1回再送 |
| `send_error_notification` / `send_recovery_notification` | 🔴障害通知（Actionsログへのリンク付き）／✅復旧通知 |
| `load_state()` / `save_state(state)` | 状態の読み書き。**破損JSONは警告して初期化**（その回は初回扱い＝通知なし） |
| `select_facilities(cfg, state, args, now)` | 2.3のTier判定 |
| `main()` | 全体フロー（3.3） |

### 3.3 メイン処理フロー

```
1  設定読込・現在時刻(JST)取得
2  稼働時間外なら正常終了（exit 0）
3  状態読込 → prev_slots（前回の枠→ステータス表）。空なら first_run=True
4  Tier判定で対象施設リストを決定（--only/--limit/--tier で上書き可）
5  施設ループ（施設間に request_interval_seconds=2.5秒のウェイト）:
   5a  早期中断: 1件も成功せず8施設連続失敗 → ループ中断（障害時の無駄打ち防止）
   5b  fetch_day → extract_slots（失敗した施設はスキップして続行）
   5c  diff_new_availability で新規空きを抽出
   5d  slot_in_windows で曜日・時間帯フィルタ
   5e  annotate_consecutive で連続時間判定（連続2時間以上とれる塊のみ）→ 通知候補に追加
6  通知判定:
   - 候補あり & 初回でない → embed構築 → Discord送信（dry-run/Webhook未設定時はログ出力のみ）
   - 候補あり & 初回 → 通知せずログのみ（誤爆防止）
7  実行成否の判定: 成功0件 または 失敗が対象の半数以上 → 「実行失敗」
   - 失敗: meta.consecutive_failures+1。3回到達 & 未通知なら🔴エラー通知（1回だけ）
   - 成功: エラー通知済みだった場合は✅復旧通知 → カウンタ・フラグをリセット
8  スナップショット更新（3.4のルール）→ 保存（dry-run時はスキップ）
```

### 3.4 スナップショット更新ルール

| 対象 | 扱い |
|---|---|
| 今回取得に**成功した施設**の枠 | 前回分を破棄し今回値で総入れ替え（消えた時間枠IDも自然に掃除される） |
| 今回取得に**失敗した施設**・対象外（Tier 2非実行回）の枠 | 前回値をそのまま保持（次回実行時に正しく差分検知できる） |
| 過去日付（今日より前）の枠 | 削除（肥大化防止） |

この設計により「取得失敗 → 次回成功」のケースでも、失敗を挟んだ前後の遷移（例: R03→A01）を取りこぼさない。

## 4. データ設計

### 4.1 枠（スロット）のキー設計

```
{施設コード}|{室場コード}|{コートコード}|{日付}|{時間枠ID}
例: 0025|001|002|2026-06-14|715
```

- 施設コードは札幌市（lgc=011002）内で一意のため、キーは全施設横断で一意
- 値は statusType 文字列のみ（例 `"A01"`）。スナップショットを最小化するため枠の詳細は保存しない（通知に必要な詳細は当回の取得データから得る）

### 4.2 通知メッセージ仕様（Discord embed）

| 要素 | 内容 |
|---|---|
| タイトル | `🟢 空きが出ました！`（2個目以降のembedは`（続き）`）、色 `#17ae9a` |
| field名 | `施設名（区）`。1024字超は`（続き）`fieldに分割 |
| field値 | 枠の行（日付・曜日・時刻・室場・コート・申込方式ラベル）を日付時刻順に列挙し、末尾に `[→ 空き状況を開く](施設の空き状況ページURL?u=利用目的ID)`。枠より広い連続塊に属する場合はラベルに `／連続枠 14:00–16:00` を付記 |
| 分割制限 | field値≦約1000字／25 fields/embed／10 embeds/メッセージ（超過時は複数メッセージ） |
| エラー通知 | `🔴 監視エラー` 色 `#ca4949`。連続失敗回数・直近エラー内容・ActionsログURL |
| 復旧通知 | `✅ 監視が復旧しました` |

### 4.3 state/snapshot.json スキーマ

```json
{
  "meta": {
    "consecutive_failures": 0,        // 連続実行失敗回数
    "error_notified": false,          // 🔴通知済みフラグ（重複通知防止）
    "last_tier2_run": "2026-06-11T16:26:40+09:00"
  },
  "slots": { "0025|001|001|2026-06-14|715": "A01", "...": "..." }
}
```

| キー | 型 | 初期値 | 意味 |
|---|---|---|---|

| `date_range_days` | int | 14 | 監視する日数（実行日起点） |

## 5. 外部インターフェース

### 5.1 取得API（詳細は調査報告書2〜3章）

```
POST {BASE_URL}/sapporo/FacilityAvailability/GetDay/{lgc}/{fc}
Content-Type: application/json（認証・トークン不要）
Body: { startDate, endDate, utilizationPurpose: [目的オブジェクト…], 他null }
→ { rooms: [室場→コート→日→時間枠(statusType)], timeFrames: [枠ID→実時刻], holidays }
```

- 1施設1リクエストで14日分×全コート×全時間枠を取得
- 複数利用目的の同時指定可（例: プレミストドーム `[4, 48]` でサッカー練習場とブルペンを一括取得）

### 5.2 通知（Discord Webhook）

```
POST {DISCORD_WEBHOOK_URL}   Body: { embeds: [...] } → 204 No Content
```

URL は GitHub Actions Secrets `DISCORD_WEBHOOK_URL` で注入（環境変数）。コード・リポジトリには含まれない。

## 6. エラー処理設計

| 事象 | 検知方法 | 挙動 | 通知 |
|---|---|---|---|
| 単一施設の取得失敗（一時的500等） | HTTP≠200 | 20秒後に新規セッションで1回だけ再試行 → 失敗ならスキップ。前回状態を保持し次回に持ち越し | なし（ログのみ） |
| WAFチャレンジ・混雑ページ | 応答が非JSON | 同上（失敗扱い） | なし |
| API仕様変更 | `rooms`/`timeFrames` 欠落 | 同上（失敗扱い） | 連続すれば🔴に集約 |
| システム全体の障害・メンテ | 先頭から8施設連続失敗 | その回の取得を中断 | 実行失敗としてカウント |
| 実行失敗の継続 | 成功0 or 半数以上失敗 が3回連続 | — | 🔴エラー通知（1回のみ）→ 回復時 ✅復旧通知 |
| スナップショット破損 | JSONパース失敗 | 初期化して継続（その回は初回扱い・通知なし） | なし（ログのみ） |
| Discord レート制限 | HTTP 429 | Retry-After秒（上限10秒）待って1回再送 | — |
| Actions実行の重複・長時間化 | — | concurrency 直列化／timeout 15分 | — |

## 9. 制約・既知の挙動

1. **対象APIは高頻度アクセス時に一時的なHTTP 500を返すことがある**（実測: 1.5秒間隔・セッション共有で18件中6件失敗 → 2.5秒間隔・施設ごと新規セッションで0件）。`request_interval_seconds` を詰めないこと
2. GitHub Actions の cron は数分〜十数分遅延しうる（Tier 1 の通知遅延は最大30分程度を許容する設計）
3. 監視対象の日付が翌日に切り替わる際、新たに範囲に入った日付の枠は「前回に存在しないキー」となるため通知されない（仕様。受付開始の検知は U02/U03→A01/L01 の遷移として捕捉される）
4. 同一枠が「空き→埋まり→空き」と再変化した場合はその都度通知される（重複抑止は「状態が変わらない限り再通知しない」の意味）
5. public リポジトリのためコード・設定・スナップショット履歴は公開される（Webhook URLはSecretsのため非公開）
6. 連続時間判定（F-8）は**同一コート・同一日の中でのみ**合算する（別コート・日跨ぎは連結しない）。先着（A01）と抽選（L01等）が隣接する場合も連続として合算する（`notify_statuses` 集合に基づくため。分けたい場合は同集合を調整）。枠の境界時刻が一致する場合のみ連結し、時間が重複する枠や飛び石は連結しない
