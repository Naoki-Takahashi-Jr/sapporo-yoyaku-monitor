## 1. 背景・目的

札幌市公共施設予約情報システム（以下「対象システム」）では、屋外サッカー場・フットサル場等の人気施設は予約枠がすぐに埋まる一方、キャンセル等により不定期に空きが発生する。空きの発生を知るには利用者が手動でサイトを確認し続けるしかない。

本システムは、対象システムの空き状況を定期的に自動取得し、**監視対象施設に新たな空き枠が発生した時点でスマートフォン（Discord）に通知する**ことで、手動確認の手間をなくし、空き枠の取得機会を逃さないようにすることを目的とする。

## 2. 対象システムの調査結果（2026-06-10 時点）

| 項目 | 調査結果 | 本システムへの影響 |
|---|---|---|
| URL | `https://yoyaku.harp.lg.jp/sapporo/` | — |
| 運営 | 札幌市（HARP 北海道自治体共同電子サービス基盤上で提供） | — |
| 空き状況の閲覧 | **ログイン不要**で閲覧可能 | 認証情報の管理が不要。監視はアカウントなしで実現できる |
| ページ方式 | **SPA（JavaScript で動的にデータを読み込む）**。施設一覧・空き状況は HTML に直接含まれない | 単純な HTML 取得では不可。内部 API の呼び出し、またはヘッドレスブラウザが必要（→ 8章） |
| 施設検索 | `/sapporo/FacilitySearch/Index` に検索 UI あり | 監視対象の特定に利用 |
| 申込方式 | 「予約申込」（先着）と「抽選申込」の2方式が存在 | **両方式とも監視・通知の対象**とする（→ F-2） |
| 利用規約 | 自動アクセス・スクレイピングを明示的に禁止する記述は**なし**。アカウントは1人1つまで等の規定のみ | 禁止されてはいないが、公共システムとして負荷への配慮は必須（→ 5.2） |
| メンテナンス | 固定のメンテナンス時間の記載なし。「予告なくサービスを停止する場合がある」 | 取得失敗は一定回数まで正常系として扱う（→ 4. F-6） |

## 3. システム概要

```
                        （15〜30分ごとに定期実行）
┌─────────────────────────────────────────────────────────┐
│  GitHub Actions（クラウド無料枠）                          │
│                                                          │
│  ┌──────────┐   ┌──────────┐   ┌──────────────┐          │
│  │ 空き状況   │ → │ 差分検知   │ → │ 通知判定      │          │
│  │ 取得      │   │ (前回比較) │   │ (条件フィルタ) │          │
│  └────┬─────┘   └────┬─────┘   └──────┬───────┘          │
│       │              │                │                  │
└───────┼──────────────┼────────────────┼──────────────────┘
        ↓              ↕                ↓
  札幌市予約システム   前回スナップ      Discord Webhook
  (yoyaku.harp.lg.jp)  ショット保存          ↓
                                      スマートフォン
                                      (Discord アプリの push 通知)
```

処理フロー：

1. 定期実行（15〜30分間隔）で監視対象施設の空き状況を実行日から14日先まで取得する
2. 前回実行時に保存したスナップショットと比較し、「埋まっていた → 空きになった」枠を抽出する
3. 抽出された枠のうち通知条件（曜日・時間帯等）に合致するものを Discord Webhook へ送信する
4. 今回の取得結果をスナップショットとして保存し、次回実行に引き継ぐ

## 4. 機能要件

| ID | 機能 | 要件 |
|---|---|---|
| F-1 | 空き状況の定期取得 | 監視対象施設（→ F-4）の空き状況を定期的に取得する。対象期間は**実行日から14日後まで**（日数は設定ファイルで変更可能）。1回の実行で監視対象の全施設・全対象日の空き状況を取得する |
| F-2 | 差分検知 | 前回取得結果と比較し、**新たに空きになった枠**（施設 × 日付 × 時間帯）のみを抽出する。「空き」は**申込方式を問わない**（先着の予約申込・抽選申込のいずれも対象とし、申込不可→申込可能への変化をすべて空き発生とみなす）。初回実行時・スナップショット欠損時は通知しない（誤爆防止） |
| F-3 | Discord 通知 | 通知条件（→ F-4）に合致した新規空き枠を、空きの発生理由（キャンセル・新規受付開始・抽選受付開始）を問わず**無条件で**通知する。通知には最低限「施設名／日付・曜日／時間帯／申込方式（予約・抽選）／予約ページの URL」を含める。複数枠が同時に見つかった場合は1メッセージにまとめる |
| F-4 | 監視条件の設定管理 | 監視対象施設・日付範囲・**曜日ごとの通知対象時間帯**を**設定ファイルで管理**し、コード変更なしで追加・変更できる。時間帯は曜日単位で自由に指定できる（1曜日に複数区間も可）。**初期値：土日＝終日、平日＝夜間（18:00–22:00）**。枠の時間が指定時間帯と一部でも重なれば通知対象とする。時間帯フィルタはすべての通知に適用される（フィルタ外の空きは通知しない）。施設ごとの監視層（Tier 1=15分間隔／Tier 2=60分間隔）も設定ファイルで変更できる。対象施設：屋外サッカー／フットサルが利用可能なスポーツ施設、および学校開放施設のうちサッカー・フットサル関係のもの |
| F-5 | 状態の永続化 | 取得した空き状況スナップショットを実行間で永続化する（GitHub Actions 環境ではリポジトリへのコミットまたは Actions Cache を利用） |
| F-6 | 異常時の通知 | 取得失敗が**連続して一定回数**（目安：3回 ≒ 1時間超）続いた場合、空き通知とは区別できる形で Discord にエラー通知を送る。単発の失敗（メンテナンス・一時障害）は通知しない |
| F-7 | 実行ログ | 各実行の結果（取得件数・差分件数・通知有無・エラー）をログとして記録し、後から確認できる（GitHub Actions の実行ログで可） |

### 通知メッセージのイメージ

> 6/14（日）13:00–15:00（予約申込）

## 5. 非機能要件

### 5.1 監視間隔・即時性（層別監視）

- 監視対象を2層に分ける：
  - **Tier 1（優先・15分間隔）**：屋外サッカー全7施設＋優先フットサル11施設（スポーツ交流施設・農試公園・中島体育センター・北ガスアリーナ札幌４６・北/東/白石/厚別/豊平/清田/南の各区体育館）＝計18施設
  - **Tier 2（60分間隔）**：宮の沢屋内競技場・西区体育館・手稲区体育館・札幌国際交流館＋学校開放39校＝計43施設
- 層の振り分けは設定ファイルで施設ごとに変更できる（F-4）
- GitHub Actions の schedule 実行には数分〜十数分の遅延が起こりうるため、cron は **15分間隔** に設定し、Tier 1 は遅延込みで30分以内の通知を担保する（Tier 2 は75分以内目安）

### 5.2 対象システムへの負荷配慮（重要）

公共システムが相手であるため、以下を必須とする。

- 1回の実行で発行するリクエスト数を必要最小限にする（取得対象は施設 × 14日分。取得 API の粒度に応じて1施設あたり数リクエスト以内を目安とする）
- リクエスト間に1〜2秒のウェイトを入れる
- 失敗時のリトライは最大1回・間隔を空けて行う（失敗の連打をしない）
- 深夜帯（目安 0:00–6:00。予約操作が行われない時間帯）は監視を停止する
- 通常ブラウザ相当のアクセスに留め、並列リクエストはしない

### 5.3 可用性

- 個人用途のためベストエフォートとする。対象システム側の無予告メンテナンス、GitHub Actions の遅延・障害による通知漏れは許容する
- ただし監視が止まったままになる事態は F-6（エラー通知）で検知できること

### 5.4 セキュリティ

- Discord Webhook URL は**シークレット（GitHub Actions Secrets）で管理**し、リポジトリにコミットしない
- 対象システムのアカウント認証情報は扱わない（閲覧のみで完結するため）

### 5.5 コスト

- ランニングコスト **0円**（GitHub Actions 無料枠・Discord 無料の範囲内）
- リポジトリは **public で確定**（public リポジトリは GitHub Actions の実行時間が無制限のため）。コードは公開されるが、Webhook URL 等の秘密情報は Secrets で管理するため公開されない

### 5.6 保守性

- 対象システムの画面・API 構造の変更により取得が失敗するようになった場合、F-6 のエラー通知で気づけること
- 監視対象の追加・変更は設定ファイルの編集のみで完了すること（F-4）

## 6. スコープ外（やらないこと）

- **予約の自動実行はしない。** 通知を受けた後の予約操作は利用者自身が行う（規約面・アカウント面のリスクを避けるため、および先着競争の公平性の観点から）
- 空き状況の Web ダッシュボード等の UI は作らない（通知のみ）
- 札幌市以外の自治体（HARP 上の他市町村）への対応は初期スコープ外とする。ただし設定で拡張しやすい構造にはしておく

| # | 内容 |
|---|---|
| 1 | 利用者のスマートフォンに Discord アプリがインストールされ、push 通知が有効であること |
| 2 | 通知用の Discord サーバー／チャンネルと Webhook を利用者が用意できること |
| 3 | GitHub アカウントを保有していること |

## 8. 技術構成案（設計フェーズへの引き継ぎ）

| 要素 | 案 | 備考 |
|---|---|---|
| 実行基盤 | GitHub Actions（schedule trigger, cron 15分間隔） | 無料・サーバー管理不要 |
| 言語 | Python または TypeScript/Node.js | 設計時に決定 |
| 空き状況取得 | **案Aで確定：内部 API（GetDay）の直接呼び出し**。1施設1リクエストで14日分×全コート×全時間枠の空き状況を取得できる。認証・トークン不要。詳細は[調査報告書](調査報告_API構造と監視対象施設.md) | 案B（Playwright 等の実ブラウザ）は WAF（Incapsula）にブロックされた場合のフォールバックとして保持 |
| 状態保存 | リポジトリに JSON をコミット（履歴が残り差分検証しやすい）または Actions Cache | 設計時に決定 |
| 通知 | Discord Webhook（Embed 形式） | 実装容易・無料 |

## 9. 受け入れ基準（このシステムの完成条件）

1. Tier 1 施設に新たな空き枠が発生してから30分以内（Tier 2 施設は75分以内目安）に、スマートフォンの Discord に通知が届く
2. 空きに変化がない場合、通知が来ない（同一の空きで繰り返し通知されない）
3. 設定ファイルの編集だけで監視対象施設・日付範囲・曜日ごとの時間帯条件を変更できる
4. 取得失敗が約1時間継続した場合、エラー通知が届く
5. 対象システムへのアクセスが 5.2 の負荷配慮要件を満たしている
6. 予約申込（先着）・抽選申込のどちらの空き発生でも通知される

## 11. 用語定義

| 用語 | 定義 |
|---|---|
| 空き枠 | 施設 × 日付 × 時間帯の単位で申込可能な状態にあるもの。先着の予約申込・抽選申込のいずれかが可能であれば「空き」とみなす |
| 新規空き枠 | 前回取得時に予約不可だったが、今回取得時に予約可能になった空き枠 |
| スナップショット | ある実行時点における監視対象全枠の空き状況の記録。差分検知の比較元 |
| 監視対象 | 設定ファイルで指定された、空き状況を取得する施設（および日付・時間帯条件）の集合 |
