## 1. 結論サマリ

1. **取得方式は「案A：内部APIの直接呼び出し」で確定**。ヘッドレスブラウザは不要（ただしWAF対策のフォールバックとして設計には残す → 7章）
2. 空き状況は **`GetDay` API 1リクエストで「1施設 × 14日分 × 全コート × 全時間枠」が取得できる**。時間枠ID→実時刻の対応表もレスポンスに同梱され、自己完結している
3. **認証・CSRFトークン・セッションは一切不要**。全APIが匿名で呼び出せる
4. **学校開放施設もスポーツ施設と同一APIで監視可能**（要件定義書10章の旧課題④は解消）
5. サッカー・フットサル関連の監視対象は **ユニーク61施設（利用目的×施設で71組）**。全件監視だと1回あたり約60リクエストになるため、施設の絞り込みまたは監視頻度の層別が推奨（→ 6章）
6. リスク：サイトは **Imperva Incapsula（WAF/bot対策）** 配下。今回の調査では通常のHTTPクライアントで全API成功したが、クラウド（GitHub Actions）のIPからのアクセスはブロックされる可能性が残る（→ 7章）

## 2. API一覧（調査で確認できたもの）

ベースURL: `https://yoyaku.harp.lg.jp`

| # | エンドポイント | メソッド | 用途 | 認証 |
|---|---|---|---|---|
| 1 | `/sapporo/FacilitySearch/SearchUtilizationPurpose` | GET | 利用目的（82件）の一覧。サッカー等のID特定に使用 | 不要 |
| 2 | `/sapporo/FacilitySearch/SearchFacility` | GET | 全施設一覧（274件）。`u`等のクエリは効かない模様 | 不要 |
| 3 | `/sapporo/FacilitySearch/Search` | POST (JSON) | 利用目的等で絞った施設＋室場の検索。**施設マスタの生成に使用** | 不要 |
| 4 | `/sapporo/FacilityAvailability/GetCalendar/{lgc}/{fc}` | POST (JSON) | 日単位の空き状況（期間指定可）。1日1ステータスの粗い粒度 | 不要 |
| 5 | `/sapporo/FacilityAvailability/GetDay/{lgc}/{fc}` | POST (JSON) | **時間枠単位の空き状況（期間指定可）。監視の本命API** | 不要 |
| 6 | `/sapporo/FacilityGuides/GetServiceProvidingTime/{lgc}/{fc}` | GET | 施設の提供時間帯（開館時間等） | 不要 |

- `{lgc}` = 自治体コード（札幌市は `011002`）、`{fc}` = 施設コード（4桁）
- 予約申込は `/sapporo/ReservationRequests/*`、抽選申込は `/sapporo/LotRequests/*`（本システムでは使用しない＝スコープ外）
- 複数施設の一括取得（`FacilityAvailability/Comparison` 画面用API）は単純GETでは確認できず。**1施設1リクエストで設計し、一括APIの有無は実装時に再確認**

## 3. 監視の本命API：`GetDay` の仕様

### リクエスト

```
POST /sapporo/FacilityAvailability/GetDay/011002/0025
Content-Type: application/json
X-Requested-With: XMLHttpRequest
```

```json
{
  "startDate": "2026-06-10T00:00:00+09:00",
  "endDate":   "2026-06-24T00:00:00+09:00",
  "roomCode": null,
  "courtSize": null,
  "utilizationPurpose": [{
    "groupId": "utilizationPurpose",
    "key": "4",
    "utilizationPurposeId": 4,
    "utilizationPurposeCategoryName": "スポーツ（屋外）",
    "utilizationPurposeName": "屋外サッカー",
    "groupName": "利用目的",
    "itemId": "utilizationPurpose4"
  }],
  "usePeople": null, "room": null, "toggleTimeType": false,
  "usageTimes": null, "usagePeriodOfTime": null,
  "allowInternetRequest": null, "requestId": null
}
```

- `startDate`〜`endDate` で期間指定（14日分が1回で取れることを実測確認）
- `utilizationPurpose` は配列。**複数目的の同時指定が可能か（＝同一施設の屋外/屋内室場を1リクエストに統合できるか）は実装時に確認**

### レスポンス（構造）

```
{
  rooms: [                       // 室場（例: サッカー場）
    { roomCode, roomName, courts: [   // コート・面（例: 東サッカー場/西サッカー場）
        { courtCode, courtName, dayBooks: [   // 日ごと
            { usageDate, usageTimes: [        // 時間枠ごと
                { usageTimeFrameId, statusType, lotRequestNumber, ... }
            ]}
        ]}
    ]}
  ],
  timeFrames: [                  // 時間枠ID → 実時刻の対応表（同梱）
    { usageTimeFrames: [ { usageTimeFrameId, usageStartTime, usageEndTime, usageTimeName } ] }
  ],
  holidays: [...]
}
```

実測例：東雁来公園サッカー場は1時間刻み（05:00〜23:00）、山鼻中学校ナイターグラウンドは「18:00-21:00」「19:00-21:00」など日により異なる夜間枠。**時間枠の粒度は施設ごとに異なるが、必ず開始・終了時刻が取れる**ため、要件の「曜日ごとの時間帯フィルタ」はこの実時刻との重なり判定で実装できる。

### 監視判定（空きステータス）

ページ内定義 `STATUS_TYPES`（15種）の全コードと監視上の扱い：

| コード | 画面表示 | 意味 | 監視上の扱い（案） |
|---|---|---|---|
| **A01** | 利用可能 | 先着の予約申込が可能 | **通知対象（空き）** |
| **L01 / L02** | 抽選申込可 | 抽選の申込受付中 | **通知対象（空き）** |
| A03 | 電話受付 | 空いているが電話でのみ申込可 | 通知対象に含める（設定で除外可） |
| U10 | 窓口受付 | 空いているが窓口でのみ申込可 | 通知対象に含める（設定で除外可） |
| A02 | 空き状況のみ | 空き表示のみ・ネット申込不可 | 通知対象に含める（設定で除外可） |
| R03 | 空きなし | 予約で埋まっている | 比較元（ここからの変化を検知） |
| L03 | 抽選待ち | 抽選結果待ち | 空きではない |
| U01 | 休館日 | — | 空きではない |
| U02/U03 | 公開前/受付前 | まだ申込期間でない | 空きではない（※受付開始でA01/L01に変わった瞬間が通知対象になる） |
| U04/U05 | 公開終了/受付終了 | 申込期間終了 | 空きではない |
| U07 | 利用不可 | — | 空きではない |
| U08 | 一般開放 | 申込対象外 | 空きではない |
| U09 | 設備保守 | — | 空きではない |

→ 要件F-2の「申込不可→申込可能への変化」は、**「非通知対象ステータス → 通知対象ステータス」への遷移**として実装する。通知対象ステータスの集合は設定ファイルで変更可能にする（初期値：A01, L01, L02, A03, U10）。

## 5. 補足調査結果

- **地区コード**：中央区10／北区20／東区30／白石区40／厚別区45／豊平区50／清田区55／南区60／西区70／手稲区75／石狩市80（検索条件の絞り込みに使用可）
- **施設分類**：屋外スポーツ01／屋内スポーツ02／文化03／その他99
- **時間帯区分**（検索UI上の定義）：午前=開館〜12:00／午後=12:00〜18:00／夜間=18:00〜閉館
- **robots.txt は存在しない**（リクエストすると「ただいま大変混雑しています」という案内ページが返る＝混雑時対応の仕組みが存在する）
- 学校開放（屋外）はナイターグラウンドが大半で、時間枠は18:00〜21:00帯。今回の実測では全枠 R03（空きなし）または U07 で、**学校開放は抽選・先約で埋まりやすい＝キャンセル監視の価値が高い**ことを裏付け

## 6. リクエスト数の試算と負荷設計案

前提：GetDay 1リクエスト＝1施設（×利用目的）×14日分。

| 監視対象 | リクエスト数/回 | 15分間隔・6:00〜24:00稼働での目安 |
|---|---|---|
| 全71組 | 約60〜71 | 約4,300〜5,100 req/日 |
| スポーツ施設のみ（u=4,30,48,49） | 約25 | 約1,800 req/日 |
| 優先施設に絞る（例：10施設） | 10 | 約720 req/日 |

設計案（いずれも要件5.2のウェイト1〜2秒を挟む）：

1. **層別監視（推奨）**：優先施設（例：屋外サッカー7＋主要フットサル施設）は15分間隔、その他・学校開放は60分間隔 → 負荷と即時性のバランスが良い
2. 全件15分間隔：実装は単純だが1回の実行が2分前後になり、対象システムへのアクセスも最多
3. 利用目的の複数同時指定（3章の確認事項）が可能なら、重複施設の統合で71組→61リクエストに削減

## 7. リスクと対策

| # | リスク | 内容 | 対策 |
|---|---|---|---|
| 1 | **Incapsula（WAF）によるブロック** | サイトはImperva Incapsula配下。今回は通常のHTTPクライアント＋ブラウザUAで全API成功したが、データセンターIP（GitHub Actions）からのアクセスや高頻度アクセスはbot判定されうる | ①ブラウザ相当のUA・ヘッダを付与 ②リクエスト間隔を空ける ③ブロック検知時（HTMLチャレンジ応答・403等）はエラー通知して停止 ④恒常的にブロックされる場合は実行基盤の変更（自宅PC/VPS）またはPlaywright(実ブラウザ)へ切替 |
| 2 | API仕様の変更 | 内部API（非公開仕様）のため予告なく変わりうる | レスポンス構造の検証を実装し、想定外構造はエラー通知（要件F-6） |
| 3 | 混雑時の制限 | robots.txt応答が示す通り、混雑時はアクセス制限が入る | リトライは最大1回・間隔を空ける（要件5.2）。混雑応答はエラー扱いにせず次回実行に任せる |
| 4 | 抽選期間の挙動 | 抽選受付開始（U03→L01）が一斉に起きると大量通知になりうる | 1メッセージへの集約（要件F-3）と、1回の通知件数上限を設計時に検討 |
